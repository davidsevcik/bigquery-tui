# 11. TUI: the decisions behind the code

Date: 2026-11-25
Status: accepted

## Context

`internal/tui` is bqt's terminal frontend: the Panes and their Layout, the Explorer and its filters, the Editor with its vim layer, the Results grid and the Sample, the Overlays, the Projects dialog and the hand-off. It draws what the core returns and keeps its own state in `state/tui.json`. These decisions were code comments until ADR 0004 moved them here.

## Decision

### Package boundary and keymap

- **`tui` (package)**: the TUI only lays out what the core returns. Every piece of product behaviour (search, ranking, sync, formatting) comes from the engine through the `Backend` interface, or, where no state is involved (a Favorite's header, matching Favorites, binding parameters), from the core package that owns the rule.
- **`tui.Backend` (Favorites)**: the Backend serves the Favorites of the current `favorites_dir`. Parsing, matching and binding parameters need no directory, so the TUI calls the `favorites` package for those.
- **`tui.Backend` (editor methods)**: the editor intelligence (`Tokenize`, `Complete`) works in byte offsets into the text, not runes or columns; callers convert cursors.
- **`tui.Zone`**: a Zone is where a key binding applies. The four Panes (Explorer, Schema, Editor, Results) are Zones too; user-visible text calls them Panes.
- **`tui.Binding`**: one entry of the keymap registry. The registry is the single source for key dispatch, the help overlay, the command palette and the footer hints, so they cannot drift apart. A key made of two tokens (`"g g"`) is a chord.
- **`tui.editingHelp`**: the text-editing keys belong to the editor widget, not to the registry, so this lists them for help separately.
- **`tui.(*rig).addViewWithFields`** (tests): adds `acme-prod.sales.v_customers`, a view with columns, and syncs it, because the shared `v_orders` fixture has no columns and the `col:` search tests rely on that.
- **`tui.rigEditing`** (tests): the `[tui]` editing style the next rig is built with. Most tests type straight into the editor, so the default is `plain`; the vim tests set `vim`.

### The state file

- **`tui.uiState`**: `uiState` is `state/tui.json`. Older bqt instances share the file and read `"layout"` as the Explorer style (`miller`, `tree`, `flat`), so `"layout"` is read but never written, and the new keys are separate.
- **`tui.uiState.PaneLayout`**: an object, so that a custom tree can sit beside the preset. It is decoded on its own, so a bad value does not lose the Explorer style.
- **`tui.lenientBool`**: reads a value that is not a boolean as false instead of failing, so one bad value does not lose the rest of the state file.
- **`tui.paneLayoutState`**: `"pane_layout"` holds the source preset, and the tree only when it differs from the preset's. The maximised Pane is never saved.
- **`tui.(*Model).loadPaneLayout`** (validation): an unknown preset (from a newer bqt) leaves `classic`, and a tree that is not valid, or that hides every Pane, gives way to its preset's tree.
- **`tui.(*Model).loadPaneLayout`** (shape): when `"pane_layout"` does not decode, the preset is still read alone, because a newer bqt may have written the tree in another shape.
- **`tui.Model.maxed`**: the maximised Pane (`""` for none) lives for the session only.
- **`tui.New`** (focus): after loading the state it focuses by MRU, because a saved Layout may hide the Explorer, the default focus.
- **`tui.New`, `tui.(*Model).closeProjects`** (hints): the state is saved right after the first-run tutorial hint is shown (at start, or when the automatically opened Projects dialog closes), so the hint shows only once.
- **`tui.tutorialRows`**: the tutorial panel has a fixed height (7 rows), not one sized to each step, so the screen does not jump between steps.
- **`tui.keyMarkup`**: highlights the backticked keys of wrapped lines and keeps its inside-backticks state across lines, because wrapping may split a key across lines.

### Layout and step-down

- **`tui.arrange`** (role): the Layout arranges the four Panes as a split tree whose leaves are the Panes (ADR 0002). `arrange` turns the tree, the body size and the focus into a rectangle per Pane; drawing and key handling both use it. Nothing in `layout.go` reads the Model.
- **`tui.arrange`** (inputs and directions): it takes the tree's source preset (whose step-down rules apply), the focused Pane, the zoom (the maximised Pane, `""` for none) and the MRU list (most recently focused first). Directions (`nav`) are worked out from the Layout before the shared slot, the fallback and the zoom, so `ctrl+w h/j/k/l` moves as on the full screen; a Pane the step-down leaves out is skipped, as `ctrl+o` skips it.
- **`tui.arrange`** (focus): the focused Pane is always on screen. If the step-down left it out, it is shown maximised.
- **`tui.Model.termH`**: the Model keeps two heights. `termH` is the terminal's rows; `h` leaves out the tutorial panel, and the body is laid out from `h`.
- **`tui.(*Model).arr`**: sizes are never cached. A resize, a Layout change, a focus change or the tutorial panel all change the arrangement, so it is recomputed for the current state.
- **`tui.(*Model).paneRect`**: returns where a Pane is drawn, or where it would be when it is not on screen, so paging by its height stays sensible while it is hidden or left out.
- **`tui.layoutNode`**: a leaf holds a Pane; a split holds children with an integer weight each. A Pane appears at most once. A hidden leaf keeps its slot but takes no space.
- **`tui.splitCol`**: a stacked split draws no separator; each Pane's title row is the divider. A side-by-side split (`splitRow`) uses a one-column separator.
- **`tui.arrangement`**: `rects` holds the Panes drawn now, each drawn exactly at its size. With the separators (and the pane bar) they tile the body with no gap or overlap.
- **`tui.classicTree`**: Explorer over Schema on the left, Editor over Results on the right. Both columns use the same weights so their rows line up: the Explorer sits beside the Editor and the Schema beside the Results.
- **`tui.presetFocus`**: the trees are in `layouttree.go`. `focus` uses the classic tree for directions but draws only the focused Pane, under a one-line pane bar.
- **`tui.presetDef`**: a named Layout. Its step-down rules also apply to edits of it: a custom Layout steps down as its source preset does.
- **`tui.presetDef.schemaBelow`**: the Schema is left out below this many columns; 0 means only when the Panes do not fit.
- **`tui.presetDef.shareBelow`**: below this many body rows the Editor and the Results share one slot; 0 means never. `browse` uses 28 body rows, which is 30 terminal rows, because the body leaves out the status and footer lines.
- **`tui.presets`**: the slice is in the `ctrl+w space` order that `nextPreset` cycles through; reordering it changes the cycle.
- **`tui.stepDown`**: the Layout as it fits the body. Below 70 columns, or when the Panes are still too small after the steps below, one Pane at a time is shown (single). Otherwise, in this order: the preset may leave out the Schema below a width; `browse` shares one slot between the Editor and the Results below a height (the one focused last is drawn, under a pane bar); and the Schema is left out when a Pane would be smaller than its minimum. The last visible Pane is never left out.
- **`tui.(*Model).revealPane`**: `browse`'s shared slot draws the one of its Panes focused last, so revealing a Pane there moves it to second place in the MRU list (right after the focused Pane) and the focus stays.
- **`tui.rawRects`**: lays the tree out by the weights alone, without the minimums. Resizing is clamped on it, so weights never drift where the screen would not change.
- **`tui.neighbour`**: the Pane `ctrl+w` moves to. Of the Panes that lie entirely on that side and overlap the current one on the other axis, the nearest; among those the most recently focused (MRU); failing that the largest overlap, then the earliest in the cycle order. The near candidates are kept in cycle order, so only a strictly larger overlap replaces the first.
- **`tui.paneAt`**: the drawn Pane whose rectangle holds screen cell (x, y), for the mouse. The body starts at screen row 0, so the rectangles are screen coordinates. A Pane's rectangle includes its title row; the separators, the pane bar, and the tutorial panel, status line and footer below the body lie outside every rectangle.

### Layout edits

- **`tui.isCustom`**: the tree operations (the presets and the `ctrl+w` window commands) are pure functions. Each takes a tree and the focused Pane and returns the new tree, or the tree unchanged with the reason for the toast. Every result is normalised, so equal layouts are equal trees and `isCustom` can compare them.
- **`tui.(*Model).editPanes`**: a tree command is refused in the `focus` Layout and in the small-terminal fallback. Otherwise the zoom is cleared first, so the result is in sight.
- **`tui.(*Model).resize`**: in `browse` below its share height the Editor and the Results share one slot, so a size change between the two would not show; the refusal says they share one slot.
- **`tui.maxWeightSum`**: bounds a split's weights (10000). Repeated edits multiply them, and a saved tree with weights above the loader's limit would be dropped. Above the bound the weights are scaled down to sum to about 1000, keeping every child at least 1; a share finer than 0.1% makes no difference on a terminal.
- **`tui.moveToEdge`**: a Pane added to an existing split along the edge gets a third of it: half the sum of the weights of the siblings that take room. Hidden siblings keep their slot but take no space, so they are left out of the sum.
- **`tui.resizePane`**: scales a split's weights up to sum to at least 1000 first, enough resolution for a 5% step.

### Overlays, keys and the mouse

- **`tui.overlay`**: each kind of popup (Jump to table, the palette, the picker, a prompt or a question, or a scrolling popup such as help or the run list) is one module behind this interface, and `render`, `key` and `footerLine` each make one call through it. As for the Panes (ADR 0002), one function lays a popup out and both drawing and the keys use it: `frame` says where the popup goes, what it draws and the window of its list, so the keys page by the rows that are shown. `frame` changes no state.
- **`tui.scrollOverlay.keep`**: runs a key's work on the popup as drawn (frame f) and keeps the window where the next frame draws it, so the window moves only with the cursor.
- **`tui.(*Model).back`**: implements "esc backs out exactly one level": each case undoes only the innermost state.
- **`tui.answerDismiss`**: kept apart from "no" because the "replace the buffer?" question treats `n` as "open the pick in a new buffer" while esc, `q` and `ctrl+c` cancel. For every other question dismiss means no.
- **`tui.(*Model).pickerKey`**: in the picker only the global ctrl keys (quit, help, cancel) still act; letters type into the search.
- **`tui.Model.pk`**: the Favorites and History picker is kept while closed, so the search typed in it survives reopening.
- **`tui.(*Model).onHistory`**: History may change between page requests, so groups already shown are skipped when a page is appended.
- **`tui.(*Model).tutorialKey`**: the tutorial does not start while a prompt or question is open, because starting it closes Overlays and would drop the question unanswered.
- **`tui.(*Model).View`**: popups leave the mouse to the terminal, so its own selection and wheel work there. Bubble Tea switches the terminal's mouse mode between frames.
- **`tui.(*Model).mouseClick`**: the mouse is off by default (the palette's "Mouse: on/off"). A left click focuses the Pane under the pointer. Both clicks and the wheel read the rectangles the Layout draws. Popups take no mouse: View asks for none while one is open.
- **`tui.(*Model).mouseOK`**: a mouse message can arrive after the mode changed (a popup opened, the mouse was turned off), so this is checked as well as View's mode.
- **`tui.(*Model).mouseWheel`** (target): scrolls the Pane under the pointer, focused or not, and the focus stays. The Explorer and the Results move their cursor through the same code as `j` and `k`, so the Schema follows and further pages load; the Schema and the Editor scroll their text.
- **`tui.(*Model).mouseWheel`** (clamp): the Schema's scroll is clamped at once, as drawing does, because several wheel steps can come between frames and would run past the end.

### Explorer and filters

- **`tui.(*Model).millerSpans`**: the Miller columns are weighted 3:5:5 (projects, datasets, tables), because dataset and table names are long and project IDs are few and short.
- **`tui.(*Model).milFirst`**: the projects column is hidden only when exactly one project is selected, not when its filter leaves one row.
- **`tui.(*Model).milLoad`** (family): an open Shard family belongs to one dataset, so it is dropped when the dataset changed under it (a project deselected, a config reload).
- **`tui.(*Model).milLoad`** (focus): an empty column cannot hold the focus, unless only its own filter emptied it.
- **`tui.(*Model).dropDeeperFilters`**: keeps the Miller rule: a column's filter lives only while the focus is in that column or one to its right.
- **`tui.(*Model).sel`**: a search result carries less than the Explorer's node, so the Explorer's node is used for it.
- **`tui.(*Model).right`**: on a row that is already open it steps into the first child, if there is one. An empty project or dataset has none and must not fall through to open, which would recurse.
- **`tui.(*Model).reveal`** (style): the `list` style cannot show projects or datasets, so revealing one falls back to the `columns` style.
- **`tui.(*Model).reveal`** (project): a pasted path can name a project that is not selected, so its project is selected first, and synced when its cache is stale. A path the catalog does not hold never gets here: `openMissing` syncs it first.
- **`tui.treeRow.more`**: set on the row after an open family's newest members: how many members it leaves out. On that row `node` is the family.
- **`tui.tree.filterOpen`**: the expansion while the filter is on, kept apart from `open` so that clearing the filter restores the rows the user had opened. A row missing from it is open when it holds a match; Shard families stay closed.
- **`tui.(*Model).filterKey`**: a new filter text resets `filterOpen`, so the new query starts from the automatic expansion, not from rows toggled under the previous one.
- **`tui.(*Model).treeBuild`**: under the filter a row is shown when it matches or holds a match; below a container that matched only by its own name, every row is shown.
- **`tui.(*Model).treeSelectNearest`**: puts the cursor on the object, or on its nearest ancestor the tree shows; the filter is cleared without opening rows.
- **`tui.familyFor`, `tui.matchedFamily`**: return the Shard family that holds the table at a path. When several could (`orders_*` and `orders_*_history` both fit `orders_<id>_history`), the one with the longest fixed parts wins.
- **`tui.matchedFamily`** (test): a filter match carries its family, so a member is found under it even when the family's fixed parts hold `YYYYMMDD` and its name reads two ways.
- **`tui.listFilter.best`**: set while typing, so the next answer moves the cursor to the best match; a reload leaves it unset and the cursor stays where it is.
- **`tui.(*listFilter).passes`**: until the first answer for the current text arrives, the list stays as it was rather than emptying.
- **`tui.(*Model).filterQuery`**: drilled into a family, the column lists its members, so the query expands shards and every member that passes is a match of its own.
- **`tui.(*Model).onFilter`** (stale): an answer is dropped when the column's parent changed while the query ran, not only when a newer keystroke superseded it.
- **`tui.(*Model).onFilter`** (families): a family that holds a matching member opens to it, as a dataset does.
- **`tui.countMatches`**: counts what a list shows: a container that holds a match is counted through that match, and a shard member through its family.
- **`tui.(*Model).schemaLines`**: a view lists its fields before its SQL (a table shows its info first), so they are in sight while writing a query.

### Editor, buffers and vim

- **`tui.editor`**: a modeless multi-line text editor: cursor, selection, snapshot undo, horizontal scrolling and a per-token highlight hook. It knows nothing about SQL; the tokens come from the core.
- **`tui.editor.vis`**: when set, the vim layer's Visual-mode selection (r1, c1, r2, c2; end exclusive). It overrides the anchor.
- **`tui.editor.inGroup`**: makes every change until `endGroup` one undo step: a vim command, including the whole Insert session it starts.
- **`tui.editor.errLine`**: the error position BigQuery pointed at, 1-based line and column; 0 means none.
- **`tui.(*editor).offset`**: the cursor as a UTF-8 byte offset into `text()`, the unit `Tokenize` and `Complete` use.
- **`tui.(*editor).deleteRange`**: removes the text between two positions without an undo push; callers push the snapshot.
- **`tui.(*editor).scrollView`**: a view scrolled further than the height allows (the Editor grew) is never moved against the wheel's direction.
- **`tui.(*Model).update`** (paste): pasted text goes in verbatim, without the typing transformations, because a tab inside a string literal matters.
- **`tui.buffer`**: one query being edited. A scratch buffer autosaves to a draft file that this instance holds under an advisory lock, so several bqt instances never overwrite each other's drafts. A file buffer saves back to its file and has no draft.
- **`tui.(*Model).saveDraft`**: the version counts as saved only once the file is really written, so a failed write (a full disk) is tried again on the next tick.
- **`tui.(*Model).finishLoad`**: a new scratch buffer's `draftVersion` is set to -1, so its draft is written on the next tick.
- **`tui.(*Model).restoreOrphan`**: the TUI records no Execution project on its drafts and compares none on restore: its buffers run in the instance's Execution project, so a draft written under a per-invocation override or a project chosen since restores without a warning. Recording one needs TUI code to keep it current and a way to show the mismatch: #131.
- **`tui.(*Model).scanOrphans`**, **`drafts.(*Store).dropLoneLock`**: a lock file without a draft is left over from an empty buffer, so it is removed when it can be locked. The check for the draft comes after the lock: only a holder writes a draft, so the answer can't change while the lock is held. Checked before, a holder could save and release in between, and the removal would drop the draft's recorded Execution project.
- **`tui.(*Model).externalEditor`**: needs `$EDITOR` or `$VISUAL` and does not fall back to the OS opener, because the opener returns at once and there would be nothing to read back.
- **`tui.(*Model).onExtEdit`**: the editor's exit is the only signal that the edit is done: bqt reads the temp file once and removes it, and never waits for a later save, since it can't tell an editor that returned early from one the user closed without changes. When the text is unchanged the toast says so and how to make an editor that returns at once wait (`VISUAL='code --wait'`), short enough to fit an 80-column footer. Trailing line breaks don't count on either side, since an editor adds or keeps one when it saves. A file that can't be read, or a buffer closed while the editor ran, is reported too, so no path drops an edit silently.
- **`tui.vim`**: vim-style editing over the same editor widget, in Normal, Insert, Visual and Visual-line modes. It is a deliberate subset (spec 9.1): counts, the usual motions, the `d c y > <` operators with motions and text objects, one unnamed register, search, and dot-repeat.
- **`tui.(*Model).editorKey`**: in Normal and Visual mode the registry keeps its ctrl and function keys, except the few vim claims (`vimClaims`: `ctrl+r` is redo, `ctrl+d` scrolls).
- **`tui.TestCtrlPOpensThePaletteInNormalMode`**: `ctrl+p` is kept from bqt in every vim mode (spec 9.1): it opens the command palette, also in Normal mode, so it is not in `vimClaims`.
- **`tui.(*vim).changeWord`**: `cw` and `cW` change to the end of the word, like `ce` and `cE`, so the blanks after it stay. It returns the motion to apply, or `""` when it changed the word's last letter itself (`ce` from there would run into the next word).
- **`tui.(*vim).applyMotion`**: `dw` on the last word of a line stops at the line end: a forward exclusive motion that crosses into a later line is pulled back to the previous line's end, as in vim.
- **`tui.(*Model).vimRepeat`** (taint): the `.` repeat itself is never recorded as the new last change.
- **`tui.(*Model).vimRepeat`** (mode): a recording always ends in Normal mode, so the repeat leaves Insert mode if the replayed keys end there.

### Runs, results and the Sample

- **`tui.grid`**: the results viewer of a Run or of the Sample: a window over pages read through its row source, with a cell cursor. It never sorts or filters; the rows are as BigQuery returned them.
- **`tui.(*grid).need`**: scroll first. After a jump (`G`) the window is where the cursor is, not where it was, and only that window is fetched: at most three pages, never the pages in between.
- **`tui.(*grid).search`**: finds the next (dir 1) or previous (dir -1) cell containing the find text in the loaded pages, starting after the cursor, and reports the number of matching cells in the loaded pages.
- **`tui.(*Model).onPage`**: a page for a grid not shown now still clears its loading mark, because the grid may be shown again (a Sample restored after the next one failed) and must not wait for the page for ever.
- **`tui.maxGrids`**: bounds the result grids kept in memory (8). A dropped grid is rebuilt from the Run when its result is opened again.
- **`tui.recordData`**: the row in the record popup is a row of the grid the Results show (a Run's or the Sample's). Grids hold clipped cells, so the row is read again in full through the grid's row source.
- **`tui.(*Model).resultsAction`**: the copy captures the cursor first, because the cursor may move while the row is read.
- **`tui.(*Model).startRun`**: in a one-Pane-at-a-time view a real Run reveals the Results, so it shows as it fills in. A dry-run does not: it has no result to show, and its estimate is in the status line.
- **`tui.(*Model).onRun`**, **`runs.(*Follower).MarkIn`**: the cursor moves to a failed Run's error position only when the buffer's text is still the version that was run, because the position only means something in that text.
- **`runs.MayBeBilled`**: a Run is treated as on-demand unless its own dry-run showed capacity, since pricing is known per Run, not per Execution project; unknown pricing counts as on-demand, the safer mistake (spec 10.2). Cancel then warns "it may still be billed".
- **`tui.sample`**: the Sample is a table's rows read free through `tabledata.list` (`Engine.Preview`) and shown in the Results Pane. It is not a Run: no job, no Run ID, no History entry, no place in the run list. There is one Sample slot per session, not per buffer, because it is about a table.
- **`tui.(*Model).samplePane`**: the Sample is titled in the success colour so a free read never looks like a billed Run.
- **`tui.(*Model).sampleAction`** (history): keeps one step back, not a chain: the previous Sample's own previous one is dropped.
- **`tui.(*Model).sampleAction`** (shards): a Shard family's Sample reads the Newest shard as it was when the Sample started, page after page, even when a sync adds a newer one meanwhile.
- **`tui.(*Model).onSample`** (not a table): when the catalog said table but BigQuery says view or external table, the Results go back to what they showed before; a Sample still loading then never finishes, so it goes too.
- **`tui.(*Model).onSample`** (switch): a switch to a Run made meanwhile is not undone.
- **`tui.(*Model).selectAction`**: `s` in the Explorer and the Schema pane writes a `SELECT` into a new buffer and never runs it; running it is billed, so the user does that.
- **`tui.(*Model).openSelect`**: a Shard family keeps its family (wildcard) path in the `SELECT`, not the Newest shard's path.

### Hand-off and Favorites

- **`tui.(*Model).openHandoff`**: the hand-off (spec 14.4) is text for an agent about the selected table or the focused Run, copied to the clipboard (OSC 52) or written to a file. The core renders the text; the TUI only picks what and where.
- **`handoff.dir`**: the default for hand-off files is relative to the working directory, so an agent started there finds them.
- **`tui.(*Model).handoffWrite`**, **`handoff.Write`**: without overwrite the file is created exclusively, so one that appeared meanwhile is not replaced.
- **`tui.confirmState.subject`**: a Favorite delete question keeps the Favorite as shown, because `favorites_dir` may change before the answer; the delete then refuses (`favorites.ErrMoved`) rather than delete another file.

### Projects, sync and pricing

- **`tui.(*Model).openProjects`**: the Projects dialog (`ctrl+x p`) chooses the Selected projects (what is synced and browsed) and the Execution project. Every key applies at once through the engine; closing the dialog starts one sync of the projects selected during the visit that have no cache or a stale one.
- **`tui.projDialog.group`**: each row's group is frozen when the dialog opens (Selected first), so toggling a project changes its checkbox, never its place.
- **`tui.(*Model).projectsHead`**: the header shows the Execution project, the keys, the selection count and the filter. Where the popup is short it drops the keys first (they are in help too), always leaving a row.
- **`tui.(*Model).afterSelectionChange`** (tick): records the applied selection, so the once-a-second tick has nothing left to do.
- **`tui.(*Model).afterSelectionChange`** (pricing): the engine forgot the old project's pricing model, so the new one is learnt.
- **`tui.(*Model).learnPricing`**: asks BigQuery how jobs are billed with a dry-run, which is free.
- **`tui.(*Model).onConfig`**: the pricing model is forgotten and learnt again when the new config may bill differently.
- **`tui.(*Model).update`** (pricing): the pricing message only redraws, because the status line reads the pricing model live.
- **`tui.(*Model).onSyncDone`**: the config may have changed while the sync held the lock (the reconcile was skipped then), so it is applied after every sync; otherwise it is a no-op.
- **`tui.(*Model).startSync`**: the sync is busy from the moment it is asked for (`syncStarting`), not only once the engine's answer arrives (`syncRunning`). Otherwise a second start in between would fail with `ErrSyncRunning` and overwrite what the first one covers. A sync of every Selected project remembers which projects were Selected when it started (`syncAllSelected`), since the engine runs it over those. The automatic refresh remembers none, because the TUI does not know which stale projects it picks.
- **`tui.(*Model).onSyncStarted`**: a start that ends with an error, or with no run (the automatic refresh found nothing to do), ends like a finished sync: the syncs queued while it was starting start now, so none is stranded.
- **`tui.(*Model).syncComing`**: reports whether the running sync, or a forced one queued behind it, covers a project. A running sync of every Selected project covers the projects Selected when it started, not those selected since. The automatic refresh covers none, because the TUI does not know which stale projects it picked. Nor does a table's sync (`gs`): it reads that one table, so it finds no other new table.
- **`tui.(*Model).startQueuedSync`**: a queued forced sync of every Selected project still adds the cached deselected projects asked for with `s`.
- **`tui.(*Model).openMissing`**: a pasted path the catalog does not hold syncs its whole project now, even when the cache is fresh, rather than fetching the one table: only a sync writes the catalog (ADR 0006), and a single fetched table would skip the dataset's location, Shard families, `ignore` and Pending datasets. A path already in the catalog (the search had not answered yet) opens without a sync, and an ignored one starts none. A running sync that covers the project is waited for, not repeated; when a forced sync of the project is already queued, the path waits for that one.
- **`tui.(*Model).openAfterSync`**: the pending path is settled by the first sync to finish with no forced sync of its project queued behind it, so a sync of another project that ran first does not report it missing. Every unit that fails during a run is recorded from its `unit_failed` event (`syncFailed`), including one that failed before the path was pasted. The project's first failure is reported instead of "not in the catalog". The result's unit errors cannot be used for this, because a unit that synced degraded (names-only or unreadable datasets) carries a summary there too. A sync that cannot start drops the path (`syncStartFailed`) unless a forced sync of its project is queued to carry it, so nothing opens later unasked.
- **`tui.(*Model).statusLine`**: the project count comes after the messages, because a config error or a sync state matters more.
- **`tui.(*Model).problemCount`**, **`sync.FindProblems`**: deselected projects are not refreshed, so their problems are not shown.
- **`sync.Problems.Warnings`**: the last sync's warnings that no unit shows already; an incomplete dataset listing is both a warning and its project's unit error.

## Consequences

- Product rules stay in the core: a TUI change that needs search, ranking, sync or formatting behaviour goes through `Backend` or the owning core package, not into `internal/tui`.
- `state/tui.json` is shared with older and newer bqt instances. Never write `"layout"`, decode each key on its own, and treat anything unknown or invalid as the default rather than an error.
- Drawing, keys and the mouse must keep reading one arrangement (`arrange` for Panes, `frame` for popups). A size worked out twice drifts.
- Asynchronous answers (filters, pages, Samples, Runs) can land after the state moved on. Each handler checks that its answer still applies, and never leaves a loading mark set for ever.
- Anything free (the Sample, the pricing dry-run, `s`) must look and act free; anything that may be billed is treated as on-demand until a dry-run says otherwise.
