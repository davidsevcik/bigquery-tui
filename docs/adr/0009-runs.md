# 9. Runs: the decisions behind the code

Date: 2026-11-25
Status: accepted

## Context

Package `runs` executes queries for every frontend: it turns a SQL snapshot into a Run, dry-runs it, asks for confirmation, submits and follows the BigQuery job, cancels it, records the History entry and serves the result page by page. Much of it guards against BigQuery behaviour that is easy to miss: jobs that outlive their caller, short responses and results that expire. These decisions were code comments until ADR 0004 moved them here.

## Decision

### One code path for every frontend

- **`runs`**: every frontend executes queries through this package, so the byte cap, the job labels and the History entry come from one code path. A Run snapshots its SQL and parameters, does a dry-run first, asks for confirmation through its state (never through a prompt), waits for a free slot, runs the job with the byte cap set, and then serves the result page by page.
- **`runs.Request`** (`Execution`): a Run given an Execution project of its own does everything there: the dry-run, the job, the result pages and the cancel, which goes to the project the job runs in. Empty means the one `Options.Execution` returns when the Run starts. Its History entry names that project, and the Run limit is shared by every Run whatever its project. A given ID that is not a valid project ID fails the Run in `Start`, before any client is built, so a mistyped ID never gets a client that stays open until `Close`; `LearnPricingIn` refuses one the same way.
- **`runs.Options`**: `Jobs` returns the BigQuery jobs client whose jobs run in a given Execution project, built lazily. A Run keeps using the client of the project it started in, so changing the Execution project does not move a Run in flight.
- **`runs.(*Run).run`** (agent policy): under an agent policy the Run never waits for confirmation. The policy has already decided: it refuses what the TUI would ask about, except a write the config allows from the CLI, which then runs without a question.

### Following a Run

- **`runs.Follower`**: a Follower follows Runs for one frontend. It keeps each Run's state as the frontend last applied it, so the frontend reacts to every change once and reads a state that only moves when it applies one. It also remembers where each Run's SQL sits in the text it came from, so an error position maps back into that text. An interactive frontend loops `Wait` in the background and `Apply` where it owns its state; an agent frontend calls `Start` and then `Outcome`.
- **`runs.Origin`**: records where a Run's SQL starts in its text (the zero-based line and column of a selection, zero for the whole text) and the version of the text it was taken from.
- **`runs.Mark`**: where a failed Run's error points in the text it ran from: a one-based line and the column as BigQuery counts it, shifted by the Origin. Every line moves down by the Origin line, but only an error on the first line is shifted by the Origin column, since later lines of a selection start at the text's own column 1. `TextVersion` names the text version the position belongs to, so a frontend does not mark a text that has since been edited.
- **`runs.(*Follower).Start`**: the Run's state is recorded as already applied in its starting state (estimating), so the first change `Wait` reports is news to `Apply`.
- **`runs.(*Follower).Confirm`**: the applied state moves from needs-confirmation to queued at once, without waiting for the Run's next change, so the frontend does not ask the question again.
- **`runs.(*Run).Await`**: blocks until the Run has changed since version `after` (0 returns the current state at once) or its end state is published, and also returns when the context ends. Calling it in a loop follows the Run without missing its final state.
- **`runs.(*Manager).Events`**: streams every Run's state changes and never blocks a publisher. When the reader falls behind, the oldest events are dropped, so the newest state always arrives.
- **`runs.TestEventsDeliverTheFinalState`**: ends by starting 300 dry-runs without reading `Events`. A reader that never reads must not block Runs; the loop has no assertion, and finishing at all is the check.

### Pricing model

- **`runs.(*Manager).learn`**: records the pricing model a dry-run revealed. A query that scans nothing and names no reservation (`SELECT 1`) says nothing either way, because BigQuery reports no reservation for it even on a reservation-backed project. The model is per project, so it is kept by Execution project (`Manager.pricing`) and recorded for the project the dry-run ran in.
- **`runs.pricingProbe`**: a free query that still needs slots (`ORDER BY` over `GENERATE_ARRAY`), so its dry-run names the reservation when there is one. A bare `SELECT 1` does not.
- **`runs.(*Manager).LearnPricingIn`**, **`runs.(*Manager).ForgetPricing`**: `LearnPricingIn` learns one Execution project's model and leaves the others alone; `""` is the one `Options.Execution` returns now. `ForgetPricing` drops every project's model, for a changed location, because the model depends on where the job runs. A change of the shared Execution project forgets nothing: each project keeps its own model, and the one of a project no longer shared is still right for a Run given that project.
- **`runs.(*Manager).LearnPricing`**: runs a free dry-run of the probe in the configured location so the first Run is presented with the right model. Without a configured location it does nothing, because the model depends on where the job runs.

### Submitting the job

- **`runs.(*Run).run`** (location): when no location is configured, the job is submitted in the location the dry-run resolved, so the results are read from there.
- **`runs.(*Run).run`** (submission): submitting is not cancelled with the Run. A cancel that arrives meanwhile is honoured right after, with the job in hand. Submission is still bounded, by the agent timeout or `SubmitTimeout`, because the client retries transient errors until its context ends. The job ID is chosen client-side before submitting, so a submission that ran out of time can still be cancelled by ID, and `Close` waits for submissions in flight so quitting cannot strand one.
- **`runs.(*Run).run`** (own deadline): when the submission deadline was the Run's own deadline, the Run's context ends with it but on its own timer. `run` waits for that context to end, so the Run ends as a timeout and not as a generic failure.
- **`runs.(*Run).run`** (submission timed out): the job may exist on BigQuery without bqt knowing, so it is cancelled by its pre-chosen ID.
- **`runs.newJobID`**: IDs are `bqt_` followed by hex only, because BigQuery job IDs allow only letters, digits, `_` and `-`.

### Cancelling and losing track of a job

- **`runs.(*Run).Cancel`**: a job that is already running is asked to cancel, and the Run stays "cancel requested" until BigQuery confirms, instead of showing cancelled while the job may still run (and bill).
- **`runs.(*Run).Cancel`** (failed request): when the cancel request never arrived, `CancelRequested` is cleared and `CancelFailed` set, so the user (or `Close`) can ask again.
- **`runs.TestFailedCancelCanBeAskedAgain`**: injects three transient `CancelJob` failures because `Manager.cancelJob` retries transient failures itself. One `Cancel` uses them all up and fails visibly; the next `Cancel` is delivered.
- **`runs.(*Run).run`** (cancelled context): a BigQuery job outlives a cancelled Go context that waits on it, so `run` explicitly asks BigQuery to stop the job.
- **`runs.(*Run).run`** (status read fails): a retryable `WaitJob` error is retried up to three times, because only the status read failed and the job itself is still running.
- **`runs.(*Run).run`** (lost track): once the status cannot be read, the outcome is unknown and the job may still be running, so it is cancelled rather than left billing with nobody watching, and the Run fails with "lost track of the job".
- **`runs.(*Run).run`** (cancelled job): a job BigQuery reports as cancelled may have been cancelled by the agent timeout, so it goes through `markCancelled`, which reports a timeout failure instead of a plain cancel.

### Shutdown and History

- **`runs.(*Manager).Close`**: cancels every Run and waits, up to 15 seconds in all, for three things. Cancel requests must be sent, because a cancel that never reaches BigQuery leaves the job running (and billing) after bqt has gone. A job being submitted must get its ID and the cancel that follows. Every Run must end, so its History entry is written before the caller closes the store.
- **`runs.(*Run).finish`**: the History entry is written before the end state is published, so whoever sees a finished Run can rely on the entry being there.
- **`runs.TestLiveReopen`**: runs a query that reads no table, so it costs nothing, then reopens its result from a second Manager, as a later bqt process does from a History entry. Run it with `BQT_LIVE_EXECUTION_PROJECT=... go test -tags live ./pkg/runs -run Live -v`.

### Locking

- **`runs.(*Manager).Start`**, **`runs.(*Manager).pricingIn`**: both call `orShared` before they take `m.mu`, never under it, because `orShared` falls back to `Options.Execution`, which reads the frontend's selection state and must not run under the Manager lock.
- **`runs.(*Manager).orShared`**: resolves an empty Execution project to the shared one for every call that can be given a project of its own: `Start`, `pricingIn`, `LearnPricingIn` and `Reopen`, all outside `m.mu`. `ReadResult` takes no project and reads through the shared one, the one `bqt mcp` keeps from its start (ADR 0008, `engine.Options` (`Execution`)).
- **`runs.(*Run).bump`**: marks a change (increments the version, closes and replaces the changed channel); the caller holds `r.mu`.

### Result pages

- **`runs.fullPage`**: reads `PageRows` rows from a start index. BigQuery cuts a response short when the rows are wide (a size limit, not the end of the result), so it keeps asking until the page is full or the result ends. Without this a short response would look like missing rows, and an export would stop early.
- **`runs.TestShortResponsesStillFillThePage`**: sets the fake's `PageLimit` because BigQuery cuts responses of wide rows short, so one row request can return fewer rows than asked. `Run.Rows` and `RawRows` must keep fetching to fill a page or an export.
- **`runs.(*Manager).trimPages`**: drops the cached result pages of all but the newest `PagedRuns` Runs, to bound memory. Their rows stay readable, because a page is fetched again from BigQuery on demand.
- **`runs.(*Manager).Reopen`**: shows the result of an earlier job (a History entry) as a finished Run. BigQuery keeps a query's result for about 24 hours; after that, or when the statement returned no rows, Reopen fails and nothing is added. The reopened Run is not recorded in History again.
- **`runs.(*Manager).Reopen`** (client): reads through the client of the entry's `execution_project`, or the shared one when the entry names none, so a Run that ran in a project of its own reads its pages there again, and needs no shared Execution project to do so.
- **`runs.(*Manager).Reopen`** (nothing runs): the reopened Run's context is cancelled at once and its done channel closed, because nothing runs: the Run is finished from the start.
- **`runs.(*Manager).ReadResult`**: reads rows of a finished job's result without a Run, because the agent surface pages a result by its job, possibly in another process than the one that ran it. A job BigQuery no longer has (it keeps results about 24 hours) is reported as `ErrGone`.

## Consequences

- No frontend may execute a query outside `runs`: the byte cap, the `bqt` labels and the History entry are applied only here.
- A started BigQuery job is never abandoned: every path that stops watching it (cancel, submission timeout, lost status, shutdown) sends a cancel, and `Close` waits up to 15 seconds for those requests. Quitting can therefore take that long.
- The History entry is written before any observer sees a finished Run; reordering `finish` breaks anyone who reads History as soon as a Run ends.
- Followers and `Await` may skip intermediate states but never the final one, and `Events` drops old events instead of blocking. A frontend must treat the latest state as the truth, not replay every step.
- Result rows are not kept: pages beyond the newest `PagedRuns` Runs and all results older than about 24 hours depend on BigQuery still holding them.
